# 渠道游戏凭据生命周期

工具保存的渠道账号凭据称为 **A**；某个游戏实际使用的完整 UniSDK 登录包称为 **B**。
这里不修改游戏内存、不注入、不伪装渠道，也不单独替换出站 SAUTH。

## 获取和复用

- 网页登录、工具启动同步和游戏启动前同步统一经过 `request_unisdk`。
- B 有明确期限且尚有 5 秒余量时复用；明确过期或服务器已拒绝的 B 不复用。
- 可以从 A 再签发 B 的渠道，B 期限未知时重新签发。B 仍可完整保存在缓存中供本次数据库投影使用，但“缓存存在”不等于“下次登录仍有效”。
- B 站、果盘等直接凭据型渠道，以及没有实现静默续签的 QQ，缺少期限时保留正常使用，直到明确过期或服务器拒绝，不捏造期限或每次强制网页登录。
- 华为采用签名时间戳约束；联想采用返回的 ST 签发时间和 TTL。保留 B 站、UC、QQ 等渠道原有的缺字段默认有效期，不在本 PR 改变兼容行为。
- 不为获取 B 额外刷新有效的 A。华为保留仍有效且绑定当前游戏的中间 access token；vivo 保留已选子账号并调用 `union/use`；OPPO 优先用已有 HTMS 签发 ticket，仅缺失或明确拒绝时恢复上游凭据一次。

## 后台与数据库

工具运行期间，每 240 秒只为确认仍在运行的游戏，刷新用户已启用游戏内切换、且已保存过 B 的华为/vivo 账号。不刷新其他已保存但未运行的游戏或未选入列表的账号。
240 秒是刷新策略，不是宣称 vivo 服务端 TTL。失败后下一周期仍可重试。

运行状态归 `Game.is_running` 管理，同一游戏（如 h55）的所有分发和安装共用，不推断某个 PID 属于哪条安装路径，也不持久保存运行状态。SDK 同时提供游戏代号与 PID 时由 `GameManager` 建立绑定；多个 PID 中还有一个存在，游戏就仍在运行。渠道刷新只读取这个游戏属性，游戏列表和启动器状态 API 也返回它，供页面展示。

普通游戏由正常 MPay 请求提供 `game_id` 和 SDK 自身的 `process_id`。后台仅用系统 `EnumProcesses` 枚举 PID，SDK 自报的 PID 仍存在就视为游戏仍在运行；PID 消失后停止刷新。按产品选择接受极低概率的 PID 复用，不引入 WMI、创建时间或额外实例校验。枚举失败时本轮跳过，不按“仍存活”处理。发烧桥接游戏沿用已校验 IPC 窗口会话的存活判断，包括已领取 ticket 的会话，不把启动意图当成已运行。

不打开游戏进程句柄，不读取进程名、路径、命令行或内存。数据库锁、修改时间、WAL 文件都不是游戏运行标志。工具启动之前已打开、此后尚未产生可观察 MPay 请求的普通游戏暂不自动刷新；可从工具重新启动游戏，启动前同步仍正常执行。

启动、游戏启动前和后台刷新沿同一准备路径，不再使用逐账号克隆、五秒并发预取和全局 Requests deadline 包装。
成功保存后，仅对用户启用游戏内切换的账号，写入完整 token、SAUTH JSON/STR、时间戳和真实渠道元数据。
不改变原生数据库文件的既有锁定、原 inode 写入和退出清理方式。

后台签发失败（包括工具启动、游戏启动前和四分钟刷新）：

1. 只把对应游戏记录标为过期并保存，其他游戏不受影响；
2. 已存在的原生账号名称标为“失效”，不将旧凭据包装成新凭据，也不凭空新建缺少 B 的账号；
3. 不逐账号 toast，不打开登录页；后台自行恢复成功也保持安静。

用户实际选中失效账号并点击登录、发起 SAUTH 时，已有请求拦截根据该账号保存的完整凭据匹配失效记录，才弹出重新登录确认窗。不需要等待服务器 403，也不会把后台续签失败伪装成游戏 403；本地拦截返回的是 HTTP 200、业务码 401，弹窗明确标注“本地拦截”，响应钩子跳过重复失败处理。只在下拉框中高亮账号、尚未发起登录请求不会触发提示。用户主动在工具里刷新/登录的失败反馈仍保留。

## 游戏 SAUTH 失败

首次真实失败立即显示非阻塞 Qt 确认窗，不必等下一次本地 401。展示实际 HTTP、`code`、`subcode` 和错误消息，并询问“登录过期，是否重新登录？”。默认选“否”；只有点“确认”才开始恢复，关闭或 10 秒未确认均不重新登录。同一账号已有确认窗时不重复叠加。所有窗口在 Qt 主线程创建，网络恢复仍在工作线程执行。

错误消息兼容明文与 Base64 UTF-8：可解码为可打印文本时显示解码结果，否则保留明文。不假定服务端消息一定经过 Base64，不新增遮蔽、截断或日志处理。只读取错误字段，不附带请求凭据。HTTP 状态与业务错误码分开显示。

用游戏、渠道、SDK UID 和实际请求的 `sessionid` 对照已保存 B；华为还对照签名绑定的 timestamp。

- 匹配当前 B：先标为失效；确认后才按账号来源恢复。
- 工具手动登录保存的渠道账号（`record_source=manual`）：尝试 A→B，无法签发才打开该账号已有的定向重新登录页，不新建另一个账号。
- 扫码/记住记录（`record_source=scan`）：没有可续签的长期凭据，确认后引导用户在游戏原生窗口重新扫码，不把账号管理页冒充扫码页，也不将记录转换成手动渠道账号。重新扫码按实际 SDK 身份更新原记录、保留名称和 UUID；观察到同一身份的新凭据 SAUTH 成功后才弹成功提示。
- “记录来源”不等于“此次从工具页面还是原生下拉点击”。手动保存的账号即使从原生下拉发起，也仍走手动账号恢复。
- 凭据不同：不把当前 B 标为失效。确认后只有非联想、唯一账号匹配时才重新投影已有完整 B，不用旧失败触发新凭据重登。
- 联想 SDK UID 固定为 `0`，不能据此猜测不同 token 属于哪个账号。
- 无法匹配：仍显示具体错误；确认后打开账号管理，让用户自行选择，原生扫码账号提示重新扫码。不修改其他账号记录。
- 确认期间账号被删除或凭据已更新时，不再恢复旧请求，而是提示重新打开游戏。

数据库更新不会刷新已打开的 MPay 表单或当前用户对象。用户确认的手动恢复完成保存和写库后，弹窗“重新登录成功，请你重新打开游戏”，15 秒自动关闭。只成功获取上游登录态、后续签发或写库失败时不报成功。
这些交互只用于用户实际登录失败后的恢复；纯后台周期不发 toast 或确认窗。

## 离线验证和实机边界

```sh
python -m compileall src
python tests/test_game_credential_lifecycle.py
python tests/test_channel_credential_reuse.py
python tests/test_honor_oracle_alignment.py
python tests/test_vivo_token_refresh.py
python tests/test_sauth_feedback.py
```

测试使用虚构凭据和模拟网络/数据库/PID 列表；Qt 测试使用 offscreen 后端验证默认否、超时、关闭、确认、去重和跨线程调度，不运行真实游戏。Windows 真实 SDK 生命周期尚未实机验收。合并前应实机检查：多开后逐个退出、PID 消失/枚举失败时停止刷新、华为/vivo 跨两个后台周期、首次 SAUTH 失败确认窗、网页取消/定向重登、原生重新扫码及数据库锁冲突。
渠道已有的有效期默认值和缺字段 fallback 保持不变。启动准备仍是静默流程；真正无法续签时先标记原生列表中的账号失效，等用户实际尝试登录该账号时再提示，不强制用户立即打开网页登录。
